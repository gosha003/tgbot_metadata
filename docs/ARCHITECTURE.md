# Архитектура

Документ для того, кто будет дописывать проект — человека или ИИ-агента.
Описывает контракт, точки расширения и ловушки, на которых здесь уже спотыкались.

## Поток данных

```
Telegram ──► bot.py ──┐
                      ├──► core/inspect.py : inspect_file(path) ──► Report ──► core/report.py
CLI ──► python -m core.inspect ──┘              │                                   │
                                               │                         render_telegram → list[str]
                                   sniff(path) → формат                  render_plain    → str
                                   family(fmt) → какой инспектор         summary_line    → str
                                               │
                        ┌──────────────┬───────┴────────┬──────────────┐
                   insp_ooxml       insp_pdf        insp_image     insp_legacy
                 docx/xlsx/pptx       pdf        jpeg/png/tiff/...  doc/xls/odf/rtf
```

Ключевое: инспекторы **не знают друг о друге**. Рекурсия (картинка внутри docx,
вложение внутри PDF, OLE-объект в `embeddings/`) — работа диспетчера
`core/inspect.py`, а не инспектора. Инспектор только помечает, что внутри есть
вложенный объект.

## Контракт: `core/model.py`

Единственная точка, через которую пять инспекторов договариваются. Менять
осознанно и целиком — против него написано всё остальное.

### `Risk`

| Значение | Что сюда | Чистится |
|---|---|---|
| `IDENTITY` | ФИО, email, GUID тенанта, серийники камеры, подписанты | да |
| `ENVIRONMENT` | локальные пути, хостнеймы, имена принтеров, строки подключения к БД | да |
| `PROVENANCE` | приложение, версия, даты, время правки, генератор, шрифты | да |
| `STRUCTURAL` | язык, теги доступности, ICC, оглавление, формат страницы | **обычно сохраняем** |

Частая ошибка: класть email или ФИО в `PROVENANCE` потому, что поле называется
`CreatorTool`. Решает значение, а не имя поля. Обратная ошибка тоже реальна —
`CreatorTool` это имя приложения и он `PROVENANCE`, хотя содержит подстроку
`creator`; на этом здесь уже ловили дефект.

### `Finding`

```python
Finding(risk, location, label, value, note="", removable=True)
```

- `location` — машинное место: `docProps/core.xml`, `/Info`, `APP1:Exif`,
  `xl/pivotCache/pivotCacheDefinition1.xml`. При рекурсии диспетчер добавляет
  префикс: `word/media/image1.jpeg > APP1:Exif`.
- `value` прогоняется через `clip()`: вырезаются управляющие символы, длина
  ограничивается. Значения недоверенные.
- **Пустое значение — это факт, а не отсутствие данных.** Пустой `dc:creator`
  означает либо предыдущую чистку, либо стоковое приложение без имени
  пользователя. Используй `add()`, чтобы показать пустое поле, и
  `add_nonempty()`, чтобы промолчать.
- `removable=False` — убрать нельзя или нельзя без потерь: таблицы квантования
  JPEG, история правок в `.doc`, цифровая подпись.

### `Signal`

```python
Signal(kind, detail, confidence="medium")   # confidence: low | medium | high
```

Это **вывод**, а не сырое значение. Виды:

| `kind` | Смысл |
|---|---|
| `producer` | чем сделан файл — только приложение/библиотека, записавшая файл |
| `ai` | признаки генерации библиотекой или ИИ |
| `dating` | датировка и геолокация по косвенным признакам: шрифт, формат бумаги |
| `scrubbed` | признаки предыдущей чистки |
| `inconsistent` | метаданные противоречат друг другу |
| `hazard` | активное содержимое: макросы, JS, инкрементальные ревизии |

`dating` отделён от `producer` намеренно. Шрифт Calibri датирует документ, но
не является приложением — пока он был `producer`, сводка выдавала «PDF, сделан
через Calibri».

`Report.signal()` **склеивает дубликаты** по паре `(kind, detail)`, сохраняя
высшую уверенность. Инспекторы ставят сигналы внутри циклов по страницам и
шрифтам, и без этого один вывод попадал в отчёт десятки раз, вытесняя остальные.

### `Report`

```python
Report(path, fmt, size=0, findings=[], signals=[], errors=[], parts=[])
```

Хелперы: `add()`, `add_nonempty()`, `signal()`, `err()`, `by_risk()`,
`count(*risks)`.

Две метрики, и путать их нельзя:

| | Что | Где используется |
|---|---|---|
| `sensitive` | IDENTITY + ENVIRONMENT + PROVENANCE | объём работы для фазы чистки; шапка отчёта |
| `critical` | IDENTITY + ENVIRONMENT | насколько всё плохо; сводная строка |

У реального PDF бывает `sensitive=137` при `critical=7`: остальное — список
шрифтов по страницам и версия формата. Назвать критичными все 137 значит
утопить семь настоящих утечек.

`parts` — состав контейнера (записи ZIP с их DOS-таймстемпами, потоки OLE).
Заполняется инспекторами, в отчёте пока не рендерится: это вход для фазы 2,
которой нужна байт-точная пересборка.

### `err()` и скраб путей

`Report.err()` вырезает абсолютные пути из текста ошибки. Текст исключения
парсера содержит полный путь к файлу **на нашей машине**, а отчёт уходит
пользователю в чат — иначе инструмент приватности сливает ровно ту категорию
`ENVIRONMENT`, которую ищет в чужих файлах.

Скраб живёт **только в `err()` и намеренно не в `add()`**: путь, найденный
внутри чужого файла, — законная находка, её надо показывать. Одинаковые по
виду строки, противоположные по смыслу.

## Определение формата: `core/sniff.py`

```python
sniff(path) -> str                 # ключ формата, НИКОГДА не бросает
unreadable_reason(path) -> tuple   # ("cloud"|"missing"|"dir"|"denied"|"other", errno)
pretty(fmt) -> str                 # человекочитаемое имя
family(fmt) -> str                 # какой инспектор обслуживает
```

Формат определяется **по магическим байтам, не по расширению** — расширение
врёт, `.docx` вполне может оказаться переименованным PDF.

### Три разных «не знаю»

Их нельзя путать, потому что пользователю нужны разные действия:

| `fmt` | Значит | Что говорить |
|---|---|---|
| `unknown` | файл **прочитан**, но сигнатура не опознана | глубокая инспекция невозможна |
| `unknown`, `size == 0` | файл прочитан и пуст | возможно, не докачался |
| `unreadable` | файл **не прочитан** | причина из `unreadable_reason()` |

Для `unreadable` причина `"cloud"` означает плейсхолдер облачного провайдера —
отчёт обязан сказать это прямо и дать действие («откройте файл в проводнике или
выберите Always keep on this device»). Раньше такой файл докладывался как
«формат не опознан» — ложный диагноз, по которому пользователь пошёл бы искать
несуществующую порчу.

`errno 22` сам по себе **не** доказывает облако: так же падает недопустимое имя
файла. Признак облака — флаги атрибутов Windows, а не errno.

### Швы для тестов

В CI не будет ни облачных плейсхолдеров, ни файлов без прав. Поэтому
`sniff._read_head` и `sniff._win_attrs` — намеренные швы: тест подменяет их
модульным атрибутом и восстанавливает в `finally`. Не потокобезопасно, для
однопоточной самопроверки достаточно.

### OLE2 определяется по верхнему уровню

`_sniff_ole()` сравнивает имена потоков **только верхнего уровня**
(`len(parts) == 1` в `ole.listdir()`). Плоский поиск по всему дереву — дефект:
вложенный OLE-объект живёт в хранилище (`ObjectPool/_1396712391/WordDocument`),
и книга Excel со встроенным документом Word определялась как `.doc`. Разбор не
тем инспектором опаснее, чем отсутствие разбора: на выходе файл, который
выглядит обработанным, но течёт.

## Отчёт не имеет права врать

Три места, где это уже ловили:

1. Подвал говорил «файл прочитан и не изменён» даже для `fmt == "unreadable"`.
   Такой файл как раз **не** прочитан. Про неизменность говорим всегда — фаза
   инспекции не пишет в файл ни при каком исходе.
2. Пустой результат при непустых `errors` докладывался как «метаданных не
   обнаружено, значит файл уже чистили». Непрочитанный файл выдавался за
   безопасный.
3. Одна битая находка уносила весь отчёт: общий `try` вместо посекционной
   деградации терял шапку, выводы и настоящие находки с PII.

## Как добавить инспектор формата

1. `core/sniff.py`: добавь ключ формата в `NAMES` (русское имя) и `FAMILY`
   (к какому семейству относится), и распознавание по магическим байтам в
   `sniff()`. **Расширение не используется** — оно врёт; `.docx` вполне может
   оказаться переименованным PDF.
2. `core/insp_<формат>.py`: функция `inspect_<формат>(path, fmt=...) -> Report`.
3. `core/inspect.py`: маршрут в диспетчере по `family()`.
4. `tests/fixtures.py`: `make_<формат>(dir) -> (путь, ожидаемые_значения)`.
5. `tests/test_inspect.py`: тест через `_check_fixture()`.

Обязательные свойства инспектора:

- **Никогда не бросает наружу.** Каждая секция разбора в свой `try/except`,
  проблема — через `report.err()`. Нам присылают битые и намеренно кривые файлы.
- **Read-only.** Вход не модифицируется никогда; это проверяется сверкой sha256
  до и после на каждой фикстуре.
- **Защита от бомб.** Проверяй несжатый размер и коэффициент сжатия до
  распаковки, ограничивай число обрабатываемых частей и глубину. Сандбокса нет.
- **Ноль обязательных внешних бинарников.** `exiftool` — только необязательное
  обогащение: нет на машине, значит работаем без него.
- **Защита от XXE.** Недоверенный XML парсится с `resolve_entities=False`,
  `no_network=True`, без раскрытия DTD.

## Ловушки, на которых здесь уже спотыкались

**Консоль Windows калечит кириллицу.** Всегда
`PYTHONIOENCODING=utf-8 python ...`. Иначе вывод превращается в кракозябры и
это выглядит как баг в коде. Артефакт cp866, а не дефект.

**Таймстемпы ZIP выдают реальное время сохранения.** Word, Excel и PowerPoint
ставят всем записям ZIP `1980-01-01 00:00`. Библиотеки (`openpyxl`,
`python-docx`) ставят настоящее время. То есть файл, заявляющий в `app.xml`
продукт Microsoft, но с реальными свежими таймстемпами записей — сделан
библиотекой, и настоящее время сохранения утекло через контейнер, даже если
`core.xml` вычищен идеально. Это сильнейший сигнал `ai`, и он не виден ни одному
инструменту, который смотрит только в `docProps`.

**Облачные плейсхолдеры OneDrive.** `os.path.exists()` → `True`,
`os.path.getsize()` отдаёт настоящий размер, а `open().read()` падает с
`OSError errno 22`. Флаг `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` (`0x00400000`).
Содержимого на диске нет. Нельзя докладывать это как «формат не опознан» —
диагноз ложный, и пользователь пойдёт искать несуществующую проблему.

**`python-docx` и `openpyxl` нельзя использовать для чистки.** Они парсят
документ в свою модель и пересобирают пакет, теряя части, которые не понимают
(`customXml/`, темы, `printerSettings`). Работать надо на уровне ZIP-записей:
`core/zipfix.py` переукладывает контейнер байт-точно (порядок записей, метод
сжатия, DOS-таймстемпы, local extra), нетронутые записи копируются сырыми
байтами.

**Сериализация XML через `lxml`/`ElementTree` тоже отпечаток.** Круг через них
переставляет объявления `xmlns` перед атрибутами (у Word среди них стоит
`mc:Ignorable`), меняет `\r\n` на `\n` и пишет `<a/>` вместо `<a></a>` — и это
видно на каждой изменённой части. Поэтому `core/clean_ooxml.py` правит части
**побайтово** по смещениям, которые сообщает `expat`: переписывается только
нужный отрезок (значение атрибута, текст элемента, сам элемент), остальное
остаётся байтами исходника.

**`mat2` для PDF растеризует страницы.** Он действительно убивает всё, но
заодно текстовый слой и поиск. Для PDF нужен `pikepdf` с точечной хирургией.

**Рендер в Telegram — только HTML, не MarkdownV2.** Экранирование надёжнее.
Все значения из файла через `html.escape`. Разрешены только `b, i, u, s, a,
code, pre, blockquote, tg-spoiler`; перевод строки — обычный `\n`. Лимит
сообщения 4096 **UTF-16 code units**, не символов; считает `_tg_len()`.

**Фото против файла в Telegram.** Отправленная «фотографией» картинка
перекодируется Телеграмом ещё до бота — метаданные уже срезаны. Бот обязан
отказывать с пояснением, иначе выдаст ложный результат на не том файле.

## Тесты

```bash
PYTHONIOENCODING=utf-8 python -m tests.test_inspect
```

`pytest` не требуется (функции названы `test_*` и совместимы с ним). Харнесс:
декоратор `_with_tmp` даёт тесту временный каталог и убирает его; `_check(name,
condition, detail)` регистрирует проверку; код возврата 1 при любом провале.

Правило: **падающий тест — ценная информация, подогнанный под баг — вредная.**
Если проверка падает из-за настоящего дефекта в модуле, правится модуль.
